# 工程方法

## 任务与完成定义

先读取 [文档导航](README.md)、[架构](architecture.md) 和 [项目状态](project-status.md)，在队列中选择一个任务，保持唯一进行中项。确定可观察验收，再按契约、实现、失败/取消/回滚验证、记录的顺序完成最小纵向切片。

实现、自动测试、原生人工验证和正式发行资格分别记录。失败应记录原因及修复后的实际复测；模拟测试不得冒充真实内核或系统写入验证。构建/测试入口见 [开发指南](development/build.md)。

### 缺陷反馈闭环

收到缺陷后先复现用户的操作顺序，区分源码构建、预览包和已发布版本；记录预期与实际状态。沿事件入口、路由、组件和状态写入定位根因，并检查同一逻辑的其他调用点。若反馈可提炼为跨页面原则，先写入交互契约，再审查同类控件与状态，避免只在截图位置补丁式修复。事前设计写明修复范围与可观察验收，再改最小连贯切片。复测既要证明原路径已修复，也要覆盖相邻路径和返回状态；未复现或未验证的情况不得写成“已修复”。

报告结果时列出实际执行的命令、产物身份、通过与失败项、未验范围。目标测试通过只表示目标路径通过；扩大套件失败时继续记录具体失败，不合并成总体通过。阶段结论使用“已实现”“自动验证”“包内验证”“原生人工验证”“正式发行合格”各自的证据，不互相推断。

## 架构原则

以下十三条是强制的。每条都说明约束什么、依据哪个已发生的问题、用什么机制强制、什么情况判定失败。执行方式（机检 / 评审）由[架构优化项清单](design/architecture-optimization-program.md#9-评审记录)登记；没有机制的条目按"指南"对待，不得当作已落地的约束。

### 原则 1：落点归属先于实现

新增能力先回答"它属于哪份既有契约"，再决定写在哪。属于既有契约（`CoreApi`、`TunSession`、`PlatformServices`、`Result`、领域类型）就必须接入；不属于才允许新建，新建抽象须有 ADR。

- 依据：新功能优先落在"最近可用位置"，因为那是唯一无需新建边界即可工作的位置。
- 强制：评审第一个问题固定为"这属于哪份既有契约"；新建抽象必须引用 ADR 编号。
- 失败样例：为第二个内核另建一套会话状态机，而 `TunSession` 已经是带测试替身的虚接口。

### 原则 2：写进契约的边界必须可机检

任何依赖方向、数量上限、禁止项，一旦写进文档，就必须有脚本或编译期约束。没有机制的，不允许写成"契约"，只能写成"现状"。

- 依据：文档声明"UI 只调 Controller"，实际有 18 处 UI 直接包含下层头文件；边界脚本 8 条检查只拦住其中 2 条。
- 强制：边界方向与上限由 `tests/test_architecture_boundaries.py` 或度量脚本断言；新增一条契约即新增一条检查。
- 失败样例：把"允许的依赖方向"写成表格，但检查脚本仍是硬编码的两条特例。

### 原则 3：收益必须可结算

优化或重构立项前，必须给出可复跑的指标，以及改动前后的两次真实输出。无法结算的改动不做，只记录为待观察。

- 依据：验证报告只记录"通过 63 组"和耗时，没有重编范围、依赖面、越层数等可结算指标；因此优化排序只能靠主观判断。
- 强制：指标由度量脚本产出，两次输出写入验证报告；没有输出的"改善"不予采信。
- 失败样例：声称"拆静态库能减少重编"，而包含关系由头文件决定，与库边界无关。

### 原则 4：一次提交一个可独立验收的切片

结构改动与功能改动分开提交。单次提交应能用一句话说清"行为变了或结构变了"，并能由单个测试目标定位。

- 依据：近 40 次提交中 19 次改动 10 个以上文件，最大一次 205 个文件、5,021 行，同时含核心、平台、应用与界面。
- 强制：提交前自查 diff 是否跨两类变更；跨类即拆分；拆分后每一片都要能单独构建通过。
- 失败样例：一个提交同时"新增双内核支持"和"精修界面"，回归失败时无法二分定位。

### 原则 5：测试要能定位，不能只报绿

新增模块必须能够在**不链接界面库**的目标中被测。确实只能整体集成测试的，必须在测试文件里写明原因。

- 依据：35 个测试目标中 26 个链接整个界面库，测试通过不区分是业务错误还是渲染副作用。
- 强制：新增测试目标只链接所需库；无法拆分时写明原因与替代断言。
- 失败样例：为验证 YAML 表单解析而链接整个 Widgets 栈。

### 原则 6：未实现的契约即债务，必须可见

设计文档里写下的接口，在实现前必须标注"未实现"，并在[项目状态](project-status.md)登记为债务项；实现完成后删除该登记。不得以"已设计"代替"已实现"。

- 依据：设计文档已列出会话端口接口但代码中不存在；全仓 0 个 TODO/FIXME 标记，债务既没有注释形式也没有清单形式。
- 强制：设计新增接口时同步登记债务项；每完成一个切片，验证报告与债务项同时更新。
- 失败样例：设计文档写明"首轮使用具体适配类型，后续统一"，统一既无编号也无排期。

### 原则 7：新能力必须走完七阶段

新能力的设计顺序固定为：**功能定义 → 技术选型 → 架构设计 → 模块设计 → 协议设计（数据库设计）→ 接口设计 → 安全设计**。每一阶段有明确产出物，产出物未落地不进入下一阶段；确需跳过的，在 ADR 写明理由与替代证据。

| 阶段 | 产出物 | 归属文档 |
|---|---|---|
| 功能定义 | 谁在什么场景完成什么任务；支持范围、使用前提、成功条件、失败后的可恢复路径 | 设计文档对应章节 |
| 技术选型 | 候选方案与不选理由；依赖、许可证、平台限制、可测试性 | ADR |
| 架构设计 | 层归属、依赖方向、状态所有者、并发与故障恢复边界、数据所有权 | [总体架构](architecture.md) + ADR |
| 模块设计 | 模块清单、模块与文件映射、职责与不变量、对外契约 | 本文件「目录与模块」 |
| 协议设计（数据库设计） | 跨模块与跨进程消息、持久化结构、版本与兼容、失败码与超时 | [内核/API 契约](api-contracts.md)、架构存储节 |
| 接口设计 | 公开签名、输入输出、错误类别、取消与幂等、状态回读 | 头文件 + 契约文档 |
| 安全设计 | 机密边界（密钥、令牌、原始配置）、权限与提权、输入校验、日志脱敏、失败降级 | ADR 或设计章节 |

本仓库没有数据库，"数据库设计"的等价物是加密索引、不可变版本目录与服务管道协议，按同一要求处理：结构变更必须同时给出兼容与拒绝策略。

涉及内核或平台写入的能力，在接口设计之后、界面之前必须先完成 SDK 级接入验证（正常、失败、并发、取消、退出）；多链路分别验证启停、观测与流量归属，真实系统接管只在隔离环境执行。

- 依据：R1 落点惯性、R6 契约未落地（定义见[架构优化项清单的根因](design/architecture-optimization-program.md#2-根因)）。不设阶段门时，实现会直接落在最近可用位置，设计文档里的接口则先于实现存在而无人跟踪。
- 强制：每个阶段的产出物出现在上表指定文档；评审核对阶段顺序与产出物。
- 失败样例：设计文档已列出会话端口接口，代码中不存在，也无债务登记。

### 原则 8：分层、松耦合、协议集成

界面侧与引擎侧（本仓库的「前端 / 后端」）都必须遵守分层：界面只经控制器命令与观测读取状态，引擎侧各层只向下依赖。模块之间只经**显式契约**交互——能力接口、领域值对象、进程协议、错误类型；不得共享内部状态、不得跨层直接取实现、不得靠文件可见性隐含耦合。

跨进程与跨模块交互一律视为协议集成：mihomo REST、TUN 服务管道、WebDAV、子进程控制各有书面协议与版本，调用方只能通过已定义的端点与帧格式访问。

- 依据：R2 边界靠约定（定义见[架构优化项清单的根因](design/architecture-optimization-program.md#2-根因)）。18 条越层 include 边与"UI 只调 Controller"的契约文字并存，说明耦合靠约定维持不了。
- 强制：依赖方向由边界矩阵检查（见[优化项清单](design/architecture-optimization-program.md)的 B 项）；新协议必须写入契约文档后才可出现调用点。
- 失败样例：界面直接包含 `profile/` 与 `storage/` 的具体头文件并自行解析持久化字段。

### 原则 9：一个模块至少一个文件

模块指可独立命名、可独立验收的职责单元：页面、可复用控件、服务适配器、协议编解码器、持久化存储、诊断出口。每个模块至少有一个实现文件；禁止把新模块写进其他模块的文件。

单文件规模是模块划分的告警而非门禁：实现文件超过约 600 行时，必须说明它为何仍属单一职责，或拆出子模块。

- 依据：R1 落点惯性（定义见[架构优化项清单的根因](design/architecture-optimization-program.md#2-根因)）。新能力一旦可以塞进既有文件，就不会产生新模块。
- 强制：模块与文件映射登记在本文件「目录与模块」；结构度量脚本检查"声明 `Q_OBJECT` 类型的头文件是否有同名实现文件"，纯头契约列入白名单。
- 失败样例：把新的页面或服务适配器追加到既有的千行文件中，使其承担两类职责。

### 原则 10：抽象是核心

先定义抽象，再写实现。重复逻辑出现第二次即提取，不允许复制粘贴后各自演化。抽象必须可替换：能用测试替身替换，且不向调用方泄漏实现细节（前置声明、能力接口、值对象）。

- 依据：R1 落点惯性、R6 契约未落地（定义见[架构优化项清单的根因](design/architecture-optimization-program.md#2-根因)）。第二个内核重复实现同一套会话状态机，而抽象早已存在。
- 强制：新增能力先给出契约类型（接口或值对象）与测试替身；评审检查是否存在第二份同类实现。
- 失败样例：为第二个后端另写一套租约与清理状态机，而不是实现已有的 `TunSession` 契约。

### 原则 11：界面也要架构化

界面同样按分层容器组织：页面 → 分区 → 工具带 → 列表/表单 → 单项，逐层嵌套。但"独立"需要判定标准，不按数量要求：

满足任一条即必须独立成模块（独立文件，并入原则 9）：
1. **可独立寻址**：在已登记的容器标识表中有条目（视图、锚点、页签、工作区、设置分类、配置任务页之一），冒烟与测试能直接定位，不靠控件对象名。
2. **可独立验收**：有以该容器为主对象的断言或用例（仅覆盖其子控件的不算）。
3. **可独立替换**：替换后不影响其他容器。

纯排版容器（只负责间距与分组，不持有业务状态、不被复用）允许写在其所属页面文件内，**不构成原则 9 的模块，不进入模块表**。本原则只约束新增或被修改的容器；存量偏差按原则 6 登记为债务，不在同一变更中扩大范围。

复用组件必须独立：被两个及以上页面使用，或承载独立交互（节点视图、延迟徽标、状态点、工具带、空态），必须成为独立模块，禁止复制后各自演化。

风格统一由机制保证而非约定：颜色、字号、间距、圆角只能来自 `ui/design` 的语义取值与 `UiTheme`；界面文件不得出现字面色值、字号或内联样式表。检查器已存在（`scripts/check_ui_tokens.py`），必须接入自动门禁。

- 依据：R2 边界靠约定、R1 落点惯性。见[根因](design/architecture-optimization-program.md#2-根因)。
- 强制：容器与组件登记到模块表；样式检查纳入构建或 CI；冒烟按路由与锚点定位，不按对象名。
- 失败样例：页面函数内直接搭多层容器，冒烟只能用控件对象名定位；样式检查器存在但没有任何工作流调用，白名单还引用已删除的文件。

### 原则 12：功能大纲与界面结构双向对应

功能清单给唯一编号，每条登记：主容器（视图 + 锚点或页签或工作区）、次要入口、命令入口、对应验收用例。容器侧反向登记它承载的功能编号。

允许一对多，但主从必须显式：**每个功能有且只有一个主容器**，次要入口可以多个（快捷入口、托盘、跨页跳转只导航，不另建配置流程）。既没有主容器、也没有登记的容器或功能，视为缺陷而非"未归类"。

大纲的入口列必须使用路由标识（视图、锚点、页签、工作区），不写自然语言描述——否则无法与代码比对，也就无法控制影响范围。

- 依据：R2、R6。见[根因](design/architecture-optimization-program.md#2-根因)。
- 强制：功能与容器的双向映射由脚本比对路由表，任一侧新增未配对即失败（见[优化项 G](design/architecture-optimization-program.md#g-功能大纲与界面结构双向映射)）。
- 失败样例：功能清单用"诊断 → 流量""维护 → 备份"这类自然语言入口，而代码一级入口是总览、配置、代理、隧道、设置；同时仓库并存 35 条 `F01` 与 17 条 `F-CORE-01` 两套编号，互不引用。

### 原则 13：必要性限制就地声明

新会话只读到被打开的文件，因此容易踩的隐含限制必须写在该文件头里，而不是只写在文档中。但头注释只承载**检查脚本表达不了**的内容，否则会与矩阵检查形成两处真相。

满足任一条的文件必须写 `// CONTRACT` 块：承担不可逆写入；持有跨线程或跨进程状态；处理机密、密钥或原始配置；定义跨版本持久化或协议格式；存在"A 之后才能 B"的隐式时序。

固定字段，整块不超过 8 行：

```text
// CONTRACT owner=<模块> layer=<目录/层>
// invariant: <必须始终成立的条件>
// forbidden: <明确禁止的操作>
// lifecycle: <生命周期或线程约束>
// tests: <守护该限制的 CTest 名，逗号分隔>
// spec: <所属契约文档>
```

- **写**：不变量、禁止操作、时序与生命周期、故障恢复边界。
- **不写**：依赖方向、数量上限、禁止 include——这些已由[架构矩阵](../tests/architecture_matrix.py)与度量脚本检查，写进头会漂移；需要时只写"见 `architecture_boundaries`"。
- **机检**：`scripts/check_contract_headers.py` 校验必需清单中的文件含完整字段，且 `tests:` 引用的用例在 CTest 中存在；字段缺失或引用了不存在的用例即失败。
- **规模**：超过 8 行说明内容属于设计文档，头里只保留要点与 `spec:` 链接。

- 依据：R6 契约未落地、R2 边界靠约定。见[根因](design/architecture-optimization-program.md#2-根因)。
- 强制：必需清单 + 用例存在性检查；新增触发文件时同步加入清单。
- 失败样例：`Append only` 一类的持久化 ID 约束只写在文档里，新会话重排枚举后旧索引无法读取，而没有任何检查或测试会因此失败。

## UI 先审视、先设计、后修改

结构约束见原则 11（容器分层、复用组件、样式统一）与原则 12（功能大纲与界面结构双向对应）；本节只规定审视与设计顺序。

1. 从完整用户任务出发，核对页面职责、操作频率、信息层级和预期；遵守 [当前交互契约](ui-interactions.md)，不只美化单个控件。
2. 修改代码前，将采用方案、布局/主次动作、浏览与写入边界、状态转换及验收点记录到所属设计章节。小改动可简短记录，大改动应说明完整操作链。
3. 设计同时覆盖空态、加载、失败、取消、草稿/候选/运行版、鼠标/键盘、窄窗/DPI/主题，以及隐藏和轻量重建。
4. 按设计实现并复核；冲突先修订设计。只有实际后果需要决策时才增加确认。测试/截图不能替代事前设计，也不能将计划自动标为通过。

### 界面组织发生在七阶段之后

七阶段（原则 7）完成到接口设计之后，才进入界面组织：从功能清单推导对象与页面归属，逐层走到所有末级任务，再组织布局和动作，最后调整间距、字阶、对比与交互反馈。视觉参考用于提炼原则，页面内容由任务和状态决定。

每项末级任务至少记录入口、目标对象、依赖的观测、主动作、失败及恢复、返回位置和可观察验收。评审先核对职责和状态，再核对层级与视觉。从现有 Qt 实现与截图验证在真实界面是否成立。

### 新增页面的检查项

1. 在 [ViewIds.h](../src/ui/ViewIds.h) 或 `Route.h` 增加稳定标识，并在 [ContainerIds.h](../src/ui/ContainerIds.h) 登记容器值。
2. 页面写成独立文件；容器满足原则 11 三条判定之一时必须独立成模块。
3. 在[需求映射](requirements-traceability.md)的主容器映射表登记承载的功能编号；`check_feature_outline` 必须通过。
4. 在 `SmokeRunner` 的旧页号期望表里登记，冒烟清单条数随之更新。
5. 若页面进入导航，同步 `fromLegacyPage` 与[交互契约](ui-interactions.md)的职责表。

### UI 操作路径与交付检查

UI 验收以用户动作链为单位：记录入口、操作前、操作后、取消/返回、再次进入，以及草稿或失败时的可见状态。逐步核对路由、页面组件、菜单锚点、焦点、滚动与业务副作用。修改共享组件时，列出所有调用页并检查每一处；不能只看改动后的单张截图。至少用一个自动用例覆盖核心转换，原生鼠标/DPI 等未执行部分明确留作未验。

完成定义同时检查页面与代码的归属、动作的实际结果和渲染证据。用路由或模型断言验证状态和数据来源，用几何断言验证对齐、换行、无遮挡与点击区，再在原生窗口检查浅色、深色、窄窗、大字号、缩放和键盘操作。按改动涉及的状态准备夹具，覆盖空、正常、等待、失败和恢复。如果改了内核或平台写入，另记 SDK、真实系统与回滚的验证条件。

构建通过后，若交付便携包，必须从**该包内的 EXE**隔离启动。冒烟按顺序切页、确认实际路由，再抓图并检查每张图对应的页面；文件数、进程退出码或单张截图不能证明全页正确。预览包记录唯一名称、SHA256 和实测路径；同产品版本的旧包不得作为新改动的证据。结果按源码测试、包内冒烟、原生人工、发行资格分开报告；扩大套件的失败逐项保留。

Windows PowerShell 调用 GUI 子系统程序时，直接使用 `& Mlash.exe` 后读取 `$LASTEXITCODE` 不能作为退出验证；用 `Start-Process -PassThru` 等待进程，再读取 `ExitCode`。冒烟证据目录每次新建，避免旧文件满足数量检查。

## 目录与模块

| 目录 | 归属 |
|---|---|
| src/domain | 值对象、列布局 ID、测速目标/TUN/快捷键的纯校验；不依赖应用、内核和 UI |
| src/app | Controller、状态、串行命令及业务协调 |
| src/core | 内核 API、进程、服务会话与就绪 |
| src/profile | YAML、下载、Provider、不可变版本与配置合成 |
| src/platform/windows | Windows 原生 API、权限、恢复及进程观测 |
| src/storage / src/diagnostics | 持久化、机密与有界日志 |
| src/ui | Widgets、按需主窗口、页面与托盘；只调用 Controller 命令。design 保存语义 token 和 Shadowrocket 特化，UiTheme 做 Qt 运行时适配 |
| resources / licenses | 运行资源、品牌与第三方许可署名 |
| docs | 当前契约、ADR、状态、验证与明确标注的归档 |
| scripts / tests | 构建验证工具与隔离测试 |
| build / dist / cores | 可丢弃构建缓存、发行暂存、固定内核；二进制不提交 |

用户数据不写回程序或源码目录。订阅路径使用随机 UUID，名称不参与路径；版本不可变，索引原子提交。原生函数不得绕过平台层进入 UI。

一个独立页面或可复用 Widget 对应一个同名实现文件，声明按需放在同名头文件。页面文件组装自己的布局和空态，主窗口按路由组合页面。需要在两页显示同一任务时，显式复用该任务的 Widget 和状态，页面各自管理布局。

模块与文件按原则 9 一一对应：新增模块时同步登记其职责与所属目录，不得追加到其他模块的文件。结构度量脚本以"声明 `Q_OBJECT` 类型的头文件是否有同名实现文件"为准检查，纯头契约（值对象、枚举、能力声明）列入白名单。

## 协作与 Git

并发协作前明确每个文件/模块的唯一写入者，接口变化先更新契约。集成者负责构建、测试和状态，不允许 UI 绕过 Controller 修补业务。委派必须有明确授权。

任务分支使用 feature/ 或 fix/ 前缀，提交采用简洁 Conventional Commit。提交包含相关契约与真实验证结果；构建输出、二进制、真实配置、订阅、令牌、日志和恢复记录不提交。

## 文档职责与优先级

原始规格作为需求基线保留；接受的偏差由编号 ADR 说明。当前架构/API/交互契约按职责维护实现，状态只记录进度，验证只记录实际结果。历史报告移入 archive 并显式标识，不作为当前缺口或验收结论。

每项事实有唯一归属；新增/移动文档必须同步导航和相对链接，执行文档与隐私检查。不得记录个人工作站路径、真实订阅、私人使用经过或会话附件标识。第三方许可署名及必要的公开项目 URL 保留。

ADR 按编号保留决策意图，后续决策可替代早期取舍，不抹除原意。当前文档重组规则见 [ADR 0041](adr/0041-public-documentation-baseline.md)。

## 资源与发行

Qt 动态链接，yaml-cpp 等依赖按锁定提交获取，编译器 ABI 不混用。现行品牌资产及应用位置见 [VI](design/u32-mlash-visual-identity.md)。`generate-brand.py` 用于追溯旧版小象资源，`generate-service-icons.py` 维护服务图标。派生资源入库，运行包无需 Python 或 Pillow。

正式发行的证据和授权材料按 [发布门禁](release-readiness.md) 管理。默认测试不改系统代理；真实写入仅在受控 VM 显式启用，失败保留恢复意图。
