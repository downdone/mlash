# U09 技术选型：Widgets / QML

状态：设计评审，未执行框架对照。**建议先保留 C++ 核心，以 Widgets 验证关键组件；QML 为明确候选，尚未采用。**

## 1. 能力与问题定位

目标是稳定导航、整组圆角列表、细线、图标、文字层级、行末命中和详情。QListView/委托、QPainter、布局和样式可以表达，QML 也可以。现有页面单体化、散落 QSS、对象树生命周期与导航错误不能直接证明 Widgets 无法完成。

QML 更便于声明组件、视觉迭代与连续动效，但不会自动修复状态语义、事务恢复或设计质量。精细感首先是排版/层级/命中/焦点正确，不是动画数量。官方定位见 [Qt 6.10 UI 技术](https://doc.qt.io/qt-6.10/topics-ui.html)。

## 2. 路线比较

| 维度 | A：Widgets 组件化 | B：独立 Quick/QML 主窗 | C：QQuickWidget 混合 |
|---|---|---|---|
| 静态截图结构 | 可实现，统一委托/组件 | 可实现，声明式表达直接 | 可实现，两套 UI 树 |
| 连续动效 | 手工、克制 | 更适合 | 受嵌入渲染影响 |
| 表格/复杂编辑 | 复用现有实现 | 重建并验输入/无障碍 | 部分复用但焦点更复杂 |
| 核心状态 | 保留 C++ | 保留 C++，增加窄桥接 | 双表现适配 |
| 轻量关闭 | 沿现有窗口树 | 明确引擎/场景图销毁 | 两种生命周期并存 |
| DPI | 支持，检查手绘资源 | 支持，检查文本/资源 | 两套均须覆盖 |
| 部署 | 当前 Widgets 集合 | Qml/Quick/Controls 等按 imports 部署 | 两种依赖同时存在 |
| 风险 | 继续堆 QSS/单体会复发 | GPU/远程会话、桥接、控件语义、部署 | 焦点、模态、渲染、销毁更复杂 |
| 取舍 | 首个候选 | 样片失败时优先替代候选 | 不作长期默认 |

“可实现”是能力判断，不是视觉/性能实测。不能预报 QML 更轻或 Widgets 必然省资源。

## 3. QML 关键约束

- QML 是 Qt 技术，不是 WebView；C++20/Core/Network/yaml-cpp 继续承担业务。
- [Controls styles](https://doc.qt.io/qt-6.10/qtquickcontrols-styles.html) 的 macOS style 仅运行于 macOS。Windows 仍需自定义视觉，不能指定样式名就获得 Apple 外观。
- [QQuickWidget](https://doc.qt.io/qt-6.10/qquickwidget.html) 需要额外离屏渲染，且限制 threaded render loop；混合不是零成本增强，但也不据此断言任何混合场景均不合格。
- [QQuickWindow](https://doc.qt.io/qt-6.10/qquickwindow.html) 资源释放与持久场景图/图形设置相关，hide 不等于完全释放。根树、引擎和 GPU 资源必须实际验证。
- 当前锁定 Qt 6.10.2；更新版文档中的新组件、StyleKit 等不能直接假设可用。升级 Qt 是独立决策。

## 4. 决策树

先按相同设计验证 Widgets 四组件：AppShell、GroupedList、NodeRow、Inspector。正常/小窗、实际 DPI、浅深、键盘均通过则继续 Widgets；不因单次审美反馈无依据换引擎。

若持续需要高复杂度手绘交互、明确需要可中断连续转场而 Widgets 在资源目标内做不到、维护对照证明组件迭代成本过高，或者 QML 样片在同条件明显更符合设计且所有门禁通过，则选择独立 QML 主窗。

页号错误、QSS 注释/选择器错误、样式遍历中销毁对象等必须治理，换引擎不保证消失。当前没有必须换框架的能力证据。

## 5. 样片计划（未执行）

同窗口、字体、缩放、合成 500 节点与相同日志/连接样本；同硬件/图形路径。比较：

1. 视觉和输入：标题居中、分隔缩进、长名、省略、延迟/详情独立命中、Tab/Enter/Esc 与可访问名称。
2. 状态：局部 busy、失败留稿、旧结果丢弃、浏览不写、主题切换不丢焦点/崩溃。
3. 生命周期：20 次关闭重开，对象/引擎/请求不累积，隐藏无页面轮询、无持续增长。
4. 资源：首次/重开时间、滚动帧时和输入延迟、客户端私有字节/工作集、CPU/句柄/GPU，记录峰值和回落趋势；不假定既有预算达标。
5. 平台：高 DPI 多屏、常用硬件与软件渲染/远程会话。macOS 承诺须有 macOS 原生证据。
6. 部署：imports 闭包、隔离 PATH/TLS、离线资源、清单/许可、无远程 QML 加载。

先定义门槛再测，同条件对照；不运行真实代理写入。组件门禁不替代受控系统/TUN/72 小时资格。

## 6. 若选择 QML：迁移方案

1. 新 ADR 替代“无 QML”的具体限制，仅表现层允许；用户已允许评估。WebView、数据库、外部任意脚本仍不引入。本轮不把评估写成已实施决策。
2. 保留 mlash_engine，通过只读 QAbstractItemModel/PresentationSession 和有限 command adapter 暴露；不公开可写 AppController，不在 QML 做文件/网络/进程或保存凭据。
3. 独立 QQuickWindow/QQmlApplicationEngine；过渡期 QApplication 可因托盘/现有工具保留。避免每页 QQuickWidget，跨窗归属、模态、焦点与关闭统一定义。
4. 按完整任务迁移，旧 UI 仅作对照或编译开关，最终一个默认主界面，不长期维护两套业务状态。
5. 先探测 Quick/Qml/Controls 可用性，再改公开 SDK 获取、CMake、部署扫描、包白名单与源码/许可。当前 34 文件包契约须重算，不能把新必需依赖删成“额外文件”。
6. UI 测试从 QWidget 查找迁为语义/模型/Quick Test 或驱动测试，核心事务与安全回归继续复用；版本锁和系统门禁不放宽。

## 7. 当前建议

本轮目标不依赖高强度动效或透明材质；先验证 Widgets 能否以合理维护成本达到设计，QML 作为认真评估的替代路线。最终若采用，优先独立 Quick 主窗+C++ 核心；本轮不改依赖、不升级 Qt、不声称任何资源优势已实测。
