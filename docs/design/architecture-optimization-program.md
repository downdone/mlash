# 架构优化项清单

本文排定架构层面的优化顺序、验收依据与实施方案。它只回答"为什么改、改什么、怎样算完成、怎么验"，不替代实现时的详细设计。当前行为以 [总体架构](../architecture.md)、[功能模块契约](../development/feature-contracts.md) 和 [交互契约](../ui-interactions.md) 为准；实际执行结果只记录在[验证报告](../verification-report.md)。产品基线仍是 [设计规格](../Mlash_Codex_Design_Spec_v2.0.md)，偏差由 [ADR](../adr/README.md) 说明。强制原则见[工程方法](../engineering.md#架构原则)。

## 1. 目的与非目标

目的：降低后续功能的边际成本，并把已经写在文档里的契约落到可机检的约束上。

非目标：
- 不改变产品行为、界面结构、持久化格式或发行资格。
- 不引入新依赖、框架、数据库、schema 迁移机制或新的平台权限。
- 不用本文替代设计。每项开工前仍按[工程方法](../engineering.md)在所属设计章节记录方案。
- 不为"看起来更整齐"做重构：凡收益无法用脚本或命令结算的改动，一律不做。

## 2. 根因

下列问题不是个别失误，而是六类机制缺失的必然产物。每条根因后给出可核对的证据，以及对立的[架构原则](../engineering.md#架构原则)；原则 7–12 是这六条的流程性与结构性补充。

### R1 落点惯性：新能力落在"最近可用位置"

单库 `mlash_engine` 同时装下 app、core、profile、storage、platform、diagnostics，因此新增能力没有"需要先建边界"的成本，默认落点永远是控制器与控制器所在库。

证据：
- `AppController` 内已有 16 个 `*Pending_` 成员声明、9 个代次计数器，用于手工协调公开命令面所覆盖的并发（脚本口径：119 个原型 + 4 个单行内联定义，多行内联未计入，故实际命令数更多）；新增一个异步预览 = 新增一个布尔加一个代次。
- 跨层数据默认用 `QJsonObject`：412 行含该 token，涉及 134 / 294 个文件。
- 第二个内核另起一套状态机：WireGuard 专属标识符 28 个，而 `TunSession` 早已是带测试替身的虚接口。

对立原则：原则 1（落点归属先于实现）。

### R2 边界靠约定，不靠机制

60 篇 ADR 记录了依赖方向的意图，但唯一的执行手段是 72 行、8 条检查的脚本，其中 3 条依赖硬编码路径。

证据：
- 度量脚本（矩阵口径）报告 20 项越层 include，现有守卫实际拦住 0 条。
- `core ↔ profile` 已是双向，且无任何检查覆盖该方向。
- UI 直接包含下层具体头 16 行（含头文件 20 行、18 个文件），与"UI 只调 Controller"的契约文字冲突，但没有检查会因此失败。

对立原则：原则 2（写进契约的边界必须可机检）。

### R3 收益不可结算

验证报告只记录"通过 63 组"与耗时，不记录依赖面、重编范围、越层数量等结构指标。结果是优化排序只能靠主观判断，且无法判断一次重构是否真的有用。

证据：
- 验证报告有完整的系统级与包内证据，但没有一项结构度量。
- 本文上一版基线在独立复核中暴露 6 项错误（结构化错误码数量、`*Pending_` 数量、测试目标数量、UI 键读取次数、翻译单元数、代次计数器数），全部源于"没有可复跑的度量"。
- 上一版把"拆静态库可减少重编"列为收益，实测证明包含关系由头文件决定，与库边界无关。

对立原则：原则 3（收益必须可结算）。

### R4 交付粒度过大

提交以"阶段合并"为单位，一个提交同时改核心、平台、应用与界面，回归失败时无法二分定位，结构债与功能变更混在一起。

证据：
- 近 40 次提交中 19 次改动 10 个以上文件。
- 排除初始提交后，按文件数最大的一次为 205 个文件、5,021 行；按行数最大为 12,651 行。另有一次 69 个文件、5,149 行，同时含 `core`、`platform`、`app`、`ui` 四个目录。
- 当前工作树另有 43 个未提交条目（38 个已修改、5 个未跟踪）、1,453 插入 / 299 删除，与本轮工作并行存在。

对立原则：原则 4（一次提交一个可独立验收的切片）。

### R5 测试层级偏集成

测试数量与质量不低（65 个用例、36 个可执行、8,441 行），但多数目标链接整个界面库，通过与否不能区分业务错误与渲染副作用。

证据：
- 36 个测试可执行中 26 个链接 `mlash_ui`；其中多数直接测试 Widgets 对象。
- 因此"63 组通过"无法回答"某个 profile 层改动是否被覆盖"。

对立原则：原则 5（测试要能定位）。

### R6 契约未落地、债务无登记

设计文档写下的接口可以先于实现存在，且没有任何清单跟踪"已设计、未实现"。仓库内没有待办标记，也没有债务清单。

证据：
- 设计文档已列出 `SessionObservation`、`prepareSession`、`disconnectSession(expectedSessionId)` 等接口，代码中并不存在。
- `src/` 下 `TODO`、`FIXME`、`HACK` 的真实标记数为 0；债务既无注释形式，也无清单形式。
- 项目状态只记录"已完成"，不记录"已设计未实现"。

对立原则：原则 6（未实现的契约即债务）。

## 3. 基线与统计口径

### 3.1 口径与可复现要求

| 术语 | 定义 |
|---|---|
| 行数 | 含空行的全部行 |
| 文件集合 | `src/` 下 `.cpp`、`.h`、`.go` |
| 计数单位 | 未特别说明时按"包含该 token 的行数"计；需要次数时另行标注 |
| 公开成员函数 | 类体 `public:` 段内的成员函数声明，原型与内联定义分别计数，signal 单列 |
| 数据成员 | `private:` 段内以 `_` 结尾的声明行，不含函数体内的使用点 |
| 翻译单元 | 仅指 `.cpp`，头文件不计 |
| 测试用例 / 测试可执行 | `add_test(` 条目数 / 测试用途的 `add_executable(` 条目数 |

基线必须绑定提交。本文撰写时工作树含未提交的界面改动，未提交状态不作为基线；表中数字标注为"工作树快照"，落地时由 P0 脚本在目标提交上重算并写入验证报告。本节全部指标必须能由一条命令复现；无法由脚本判定的表述不得写入效果表。

### 3.3 越层 include（矩阵口径）

矩阵定义与白名单在度量脚本内维护：`diagnostics` 为横切服务，各层可向其写入；`storage` 位于 `platform` 之上、`core`/`profile` 之下；界面可依赖全部下层。

| 方向 | 边数 | 典型位置 |
|---|---|---|
| `core` → `profile` | 3 | `CoreUpdate.h`、`OfficialCoreSource.h`、`TunPolicy.cpp` |
| `core` → `app` | 2 | `TunSession.cpp`、`WireGuardSession.cpp` 引用 `app/Async.h` |
| `profile` → `core` | 1 | `SubscriptionDownloader.h` |
| `profile` → `app` | 1 | `WebDavClient.cpp` 引用 `app/Async.h` |
| `platform` → `core` | 3 | `TunNative.cpp`、`TunServiceMain.cpp` |
| `platform` → `profile` | 1 | `WireGuardService.cpp` |
| `platform` → `storage` | 4 | `ProxyCoordinator.cpp`、`TunNative.cpp`、`TunServiceMain.cpp`、`WireGuardService.cpp` |
| `diagnostics` → `app` | 2 | `QualificationRun.h/.cpp` |
| `diagnostics` → `ui` | 2 | `QualificationRun.h` |
| `diagnostics` → `storage` | 1 | `QualificationRun.cpp` |

合计 20 条，现有守卫实际拦住 0 条，见 R2。界面到下层另有 20 条 include，按当前矩阵允许（界面可依赖全部下层）；若将来收紧界面依赖，需另立规则并同步白名单。

### 3.4 已成立的四条边界

- Win32 头与原生函数未出现在 `src/platform` 之外。
- UI 无直接网络与进程调用。
- `src/app` 不依赖 `src/ui`。
- 无 `friend`、无单例、无全局可变状态。

## 5. 优化项与实施方案

以下每项统一给出：目标、依据、措施、效果、实施方案（文件级改动与步骤）、验证（命令与期望）、回滚、完成定义。

### P0 基线度量脚本

**目标**：让本文所有数字可由第三方一条命令复现，避免基线随工作树漂移。

**依据**：R3。上一版基线在复现中出现 6 项偏差，均因口径未定义、无脚本可查。

**措施**：
1. 新增 `scripts/measure-architecture.py`，只读源码，仅用标准库。
2. 输出 §3.2 全表，每项指标在脚本内注明计算口径。
3. 提供 `--check` 模式：与脚本内基线常量比较，漂移即失败。
4. 纳入自动检查：优先 `find_package(Python3 COMPONENTS Interpreter)` 注册独立 CTest 项；找不到 Python 时退化为在 `scripts/test.ps1` 末尾调用，并在文档写明实际采用哪一种。

**效果**：指标可复现；任何"指标改善"的结论必须先给出脚本前后两次输出。

**实施方案**：
1. 新文件 `scripts/measure-architecture.py`（约 260 行）：实现 9 组指标——文件与行数、`AppController.h` 公开声明（原型/内联/signal）、`*Pending_` 与代次计数器声明数、`QJsonObject` 行数、越层 include 行数、包含 `AppController.h` 的翻译单元数、`add_test` 条数、链接 `mlash_ui` 的测试目标数、模块与文件覆盖（声明 `Q_OBJECT` 的头文件是否有同名实现文件，纯头契约列入白名单；超过约 600 行的实现文件列入告警清单，不算失败）。
2. 指标实现规则写入脚本顶部注释，与 §3.1 一一对应。
3. `--check` 比较值定义为脚本内 `BASELINE` 字典；首次运行用 `--write` 生成并人工核对后写回。
4. 复用 `CMakeLists.txt` 已有的 `Python3` 探测块，注册 `architecture_metrics` 与 `architecture_metrics_self_test`；探测失败时不注册，不影响配置。
5. `docs/engineering.md` 验证节加入命令；本文 §3 标注脚本路径与基线提交。

**验证**：
- `python scripts/measure-architecture.py`：输出与 §3.2 逐行一致。
- 连续运行两次：输出完全相同（无时间戳、无字典序漂移）。
- 负向用例：在临时副本中人为改动一个指标后 `--check` 必须返回非零；不得通过修改真实工作区制造失败。
- `./scripts/test.ps1 -Preset windows-mingw -TestRegex '^(architecture_metrics)$'` 通过（或按退化方案在 `test.ps1` 输出中出现该检查）。

**回滚**：删除脚本并撤销 `CMakeLists.txt` 的 8 行；无运行时影响。

**完成定义**：
- 实现：脚本对 §3.2 每一项都有稳定输出；口径与脚本注释一致。
- 自动验证：`--check` 正向通过、负向失败各一次，两次输出写入验证报告。
- 文档：本节标注脚本入口与基线提交；工程方法验证节加入命令。
- 不改范围：脚本只读源码，不写业务数据、不联网、不修改工作区。

### A 会话清理闸门统一

**目标**：把散落在 6 个翻译单元、13 处的租约判断改成单一谓词与单一文案来源。

**依据**：
- `wireGuard_.leasePending()` 作为写操作前置拒绝条件共 13 处：`AppControllerRuntime.cpp:42/92/104/115/142`、`AppControllerWireGuard.cpp:28/81/82/159`、`AppControllerTransaction.cpp:18`、`AppControllerProfiles.cpp:463`、`AppControllerProxySwitch.cpp:17`、`AppControllerLifecycle.cpp:87`。
- `TunSession` 已是虚接口，含 `start`/`stop`/`ready`/`active`/`observation`/`confirmCleanup`，且已有测试替身（[TunTests.cpp](../../tests/TunTests.cpp) 的 `FakeTun`）。真正的问题是 `WireGuardSession` 未适配这套契约，并重复实现了同一套管道、代次、租约与清理状态机（R1）。
- 重复直接导致 13 处各自判断，条件与文案无法保证一致。

**措施**：
1. `src/domain` 增加 `CleanupState` 枚举（无租约 / 待确认 / 已确认 / 失败）与纯函数 `canStartSession(CleanupState)`。
2. `TunSession::observation()` 已输出 `cleanup_pending`；`WireGuardSession::observation()` 增加同名字段，两者都映射到 `CleanupState`。
3. 应用层提供唯一文案函数 `sessionBlockReason(CleanupState)`；13 处改为调用同一谓词与同一文案。
4. 不新增端口抽象、不改公开命令签名、不动 UI。

**效果**：

| 指标 | 基线 | 目标 |
|---|---|---|
| `leasePending()` 直接调用点 | 13 | ≤ 2（仅适配与观测内部） |
| 清理拒绝文案定义处 | 13 处各自拼装 | 1 处 |

**实施方案**：
1. 新增 `src/domain/CleanupState.h`（约 40 行，纯头文件）：枚举 + `canStartSession`。

- u40 清单的"主要入口"列仍是 U40 提案用语（"诊断 →"出现 6 次），而代码一级入口只有总览、配置、代理、隧道、设置（[ViewIds.h](../../src/ui/ViewIds.h) 的 7 个视图加工作区与页签）；两套命名无法自动比对。
- 因此清单只能人工对照，回答不了影响域问题。这正是原则 12 要消除的状态。

**当前状态**：容器注册表 `src/ui/ContainerIds.h` 与检查脚本 `scripts/check_feature_outline.py` 已落地。G1 已把 U40 的 32 条任务并入主容器映射（`F-U40-01`–`F-U40-35`，对应清单 `F01`–`F35`），`RESERVED` 从 21 条减到 7 条，只余结构性父容器、待定的总览视图和 U40 未收录的隧道工作区；`F14` 拨号链、`F32` 快捷键、`F33` 外观缺已登记容器，暂未映射，是否新增登记值待决。U40 清单已在原位标注为 U40 时期提案，尚未移入归档目录。

**措施**：
1. 功能编号只保留一套：以[需求映射](../requirements-traceability.md)为唯一归属，把 u40 的 35 条任务并入或映射，原文件标注为 U40 时期提案并归档。
2. 每条功能增加"主容器"列，取值必须是路由标识（视图、锚点、页签、工作区），如 `Profiles`、`Data+Connections`、`Settings+Maintenance`。
3. 容器侧反向登记：由脚本从主容器列生成"承载功能编号"清单，不手写。
4. 新增 `scripts/check_feature_outline.py`：解析两份表格与 `ViewIds.h`、`Route.h` 常量，双向比对；任一侧新增未配对即失败。
5. [交互契约](../ui-interactions.md)的页面职责表改为指向该映射，避免三份职责表并存。

**效果**：

| 指标 | 基线 | 目标 |
|---|---|---|
| 功能编号体系 | 2 套，互不引用 | 1 套 |
| 入口列可机检比例 | 0（自然语言） | 100%（路由标识） |
| 未配对功能或容器 | 无法统计 | 0，脚本失败即阻断 |

**实施方案（2 切片）**：
1. 切片 G1 收敛编号：把 u40 清单标注为历史提案并移入归档；在需求映射中增加"主容器"列，先填现有 17 条，再把 35 条用户任务逐条归属到已有编号或新增编号。
2. 切片 G2 机检：编写 `scripts/check_feature_outline.py`（约 150 行），解析表格与常量，输出未配对清单；注册到检查；负向用例——临时增加一条未配对条目必须失败。

**验证**：
- `python scripts/check_feature_outline.py` 输出未配对 0。
- `python scripts/check_docs.py` 在归档移动后仍全部可达。
- 负向用例：临时增加一条功能但不写主容器，脚本必须失败，随后撤销。
- 人工抽查 3 条功能：按主容器列能直接定位到对应页面与页签。

**回滚**：归档移动可逆，新增列可删除，脚本为单文件。

**完成定义**：
- 实现：单一编号体系；入口列全部为路由标识；反向清单由脚本生成。
- 自动验证：正向通过、负向失败各一次，输出写入验证报告。
- 文档：交互契约指向该映射；归档文件标注生效日期。
- 不改范围：不改界面结构与行为，本项只建立映射与检查。

**风险**：35 条任务归入 17 条编号需要判断，可能出现"一功能多编号"。措施是允许一条任务挂多个编号，但不允许两个主容器；归属存疑的条目单独列出并在评审中定案。

## 6. 暂缓与不做

### 6.1 暂缓：拆分 `mlash_engine` 静态库

理由：
- 收益论证不成立：26 个链接 `mlash_ui` 的测试多数直接测试 Widgets 对象，不链接 Widgets 的目标拆库后仍需 Widgets。
- 重编收益不成立：包含关系由 `AppController.h` 决定，与库边界无关；该收益已由 D 承接。
- 代价被低估：实测需先搬迁 5 条越层边，`core ↔ profile` 已是双向，`MlashTunService` 同时需要 core、profile、storage，实际需 7–8 个库与 4–5 个切片。

按原则 6，本项作为**已设计未执行**的债务登记于此，状态为"暂缓"，不进入进行中项。

重启条件：B 与 D 完成后仍存在无法用脚本表达的边界诉求，且真实 Wintun/路由/DNS 已通过受控验收。

### 6.2 暂缓：完整会话端口抽象

理由：真实 Wintun 接口、系统路由与 DNS 尚未在受控环境验收（见 §8）。语义未稳定时建立端口会锁定错误抽象。A 已交付该项当前可确定的部分。按原则 6 登记为债务。

重启条件：WireGuard 系统级验收通过，且出现第三个后端需求。

### 6.3 明确不做

| 不做 | 理由 |
|---|---|
| 引入依赖注入框架或事件总线 | 现有构造注入与单一写入者已足够，会与有限 worker、串行写冲突 |
| 更换 Qt 版本或转向 QML | QML 被规格排除；精确版本是可复现性资产 |
| 引入数据库或 schema 迁移框架 | 便携分发与 256 份订阅规模下加密单文件更合适 |
| 重写界面层 | 现有界面有原生截图与几何断言支撑，重写是纯风险 |
| 改单实例锁或索引大小上限 | 与恢复语义绑定，属产品决策而非重构 |
| 四类设置对象强类型化 | 已有严格校验，改造收益是可读性，却引入拒绝未知键的只读风险 |
| 用模拟结论替代系统验收 | 违反"只有运行证据可升级结论" |

## 7. 门禁

每个切片的统一门禁：

1. 在[项目状态](../project-status.md)登记进行中项；允许并行切片，但每个切片独占文件、各自登记、各自过门禁，共享文件同一时间只允许一个写入者。
2. 改代码前把方案写入所属设计章节；涉及界面绑定的 A、C、E 还需通过"先审视、先设计、后修改"。
3. 构建、定向测试、默认全量回归；失败修完再进入下一片。
4. 同步架构、功能契约与新增 ADR；验证报告只写实际执行结果。
5. 结论按实现、自动验证、包内验证、原生人工验证、发行资格分别记录。
6. 任何"指标改善"必须附度量脚本前后两次输出（原则 3）。
7. 结构改动与功能改动分提交（原则 4）；新增测试目标只链接所需库（原则 5）。
