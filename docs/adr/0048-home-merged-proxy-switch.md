# ADR 0048：首页合并为「代理控制 + 节点」，主控件改为代理总开关

2026-10-30 · 已接受（切片 R3、R3b 落地）。本 ADR 取代 [ADR 0047](0047-website-tests-and-title-removal.md) 中「首页含状态/节点」的页签归属，以及 [U06 结构裁决表](../ui-layered-design.md#结构裁决表) 中「状态页主控件 = 内核启动/停止按钮、状态与节点分属两个页签」的决定；取代 ADR 0046 中「分区页签承载视图名」对首页的适用，以及 ADR 0043 中「首页节点预选须显式点击『切换』才提交」与其验证边界「节点预选零写入」。取代 ADR 0046「命令集合、状态字段与持久化 schema 不变」中**命令集合**一句（见下方「Controller 影响」）。分区名、四分区数量、路由键 `(viewId, category)` 与设置三分类**不变**。

## 原因

2026-10-29 的外部评审（Shadowrocket 桌面参照，报告存档于对话，未入库）指出三处与我们设计相悖的事实，经与三张实机截图逐项核对成立：

1. **状态与节点被拆成两个页签，代价落在最高频任务上。** 用户打开应用最常做的是「开/关代理」与「换节点」。当前设计把它们分置两个页签，换节点需要先切页签；而截图显示 Shadowrocket 首页在同一屏内完成状态、开关、路由模式、连通性测试与节点选择。
2. **主控件语义与用户意图错位。** 「停止内核」是技术动作，用户的心智是「关掉代理」。以 `AppController::startCore/stopCore` 为唯一主按钮，会把「内核在跑但没接管流量」这一状态交给用户自己从状态句里推断。
3. **首页控件预算没有用在正确对象上。** U06 为状态页定了「≤3 个可交互元素」并据此裁到只剩一个按钮 + 一个分段，却仍要用户切页签才能选节点——预算省下来了，路径没缩短。截图的事实是：3 个元素指的是**控制区**，节点列表在控制区之下，不是被删掉。

## 决定

**首页合并为一个滚动视图：控制区在上，节点列表在下。** 首页不再有「状态/节点」两个页签。实施顺序：R1 只做路由归一化（索引 2 保留为同一首页的节点入口）；R3 把节点列表并入索引 0 的滚动视图并删除索引 2 的控件实例。两片之间节点区仍可用。

顺序固定为：

```
① 当前代理     当前成员 / 策略组            [代理总开关]
② 路由方式     规则 / 全局 / 直连            [选择器]
③ 连通性       上次结果 + 时间               [测试]
─────────────────────────────────────────
   订阅选择器   搜索  排序  测速  筛选
   节点与策略组列表（分组、可折叠、行内延迟、当前成员标记）
```

**主控件 = 代理总开关，不是内核启停。** 具体规格：

| 项 | 规格 |
|---|---|
| 形态 | 按钮或开关均可，但**文案必须带动词与结果**：「开启代理」/「关闭代理」；执行中显示「正在开启…」「正在关闭…」 |
| 语义 | 「让用户选择的接管方式生效/失效」。点击开启时，若内核未运行则内部先启动内核，再按设置恢复系统代理/TUN；点击关闭时只撤销系统代理/TUN，**内核继续运行**（供测速、配置管理与快速重开） |
| 内核可见性 | 状态句报告内核状态（运行中/启动中/已停止/失败），**但内核单独启停不是首页控件**；它移至「更多运行信息」与托盘 |
| 失败 | 不在开关上虚报成功；状态句给出失败原因与重试入口 |
| 三态分离 | 内核 / 接管（系统代理+TUN）/ 目标可达性**分别报告**，任一组合都不得显示自相矛盾的「已连接」 |

**节点切换在首页直接生效，取消提交条。** 手动策略组（`select` 类）点击成员即调 `selectMember`，失败回滚为原成员并就地提示。自动策略组（`url-test`/`fallback`/`load-balance`）**不得**提供行内「切换」语义，只展示当前选路结果。既有的「固定到某节点 / 恢复自动」（`selectMember` 对 `URLTest`/`Fallback` 的写入口）**保留但不进首页行内**，收进节点区「其余操作」：它是低频显式动作，与行内单击是两种语义。`load-balance` 在运行时被 `selectMember` 拒绝，属自动组，按只读处理；`AppController` 需把组类型判定统一为一处（现状 `homeNode`/`websiteNode`/`selectMember`/`clearAutomaticSelection`/托盘各写一份，且都不认 `load-balance`）。

**首页控件预算改口径。** 由「≤3 个可交互元素」改为：**控制区 ≤ 6 个控件，节点列表不计入**。理由：截图证明状态与节点同屏是可行的，硬凑 3 会以路径长度为代价。

## 影响与约束

- **分区页签在首页消失。** 首页成为唯一无页签视图（ADR 0047 的「页签承载视图名」对首页不再适用）；窗口标题仍显示「Mlash · 首页」，供 Alt+Tab 识别。其它分区的页签规则不变。
- **`startupPage` 数值不变**，0 与 2 都落到首页；入口 2 传入时定位到节点列表（R1：节点入口视图并定位当前成员行；R3：首页内滚动到列表首行）。不迁移数据。
- **托盘与状态条仍是代理总开关的次入口**，行为必须与首页同源（同一 Controller 调用、同一确认规则）。托盘还需补「启动内核 / 停止内核」两项——上文说内核单独启停移到「更多运行信息」与托盘，原托盘树漏列。
- **需要一个新的 Controller 命令 `setProxyEnabled(bool)`。** 初稿曾决定「UI 层按固定顺序编排现有命令」，经逐行核对 `AppController` 后判定**不可行**：

  | 阻碍 | 代码事实 |
  |---|---|
  | 不能并发调用 | `begin()`（`AppController.cpp:139`）在 `state_.busy` 时直接拒绝并 emit 失败；第二步会在第一步 `finish()` 之前被拒 |
  | 无法得知完成 | `startCore()`（`:424`）在内核已运行时**静默 return**，UI 收不到任何信号 |
  | 顺序不成立 | `setSystemProxy(true)`（`:528`）要求 `state_.ready && Running`，而 `ready` 只在 activation 回读通过后置位——必须先等内核就绪事件，不是顺序调用 |
  | 不是并列步骤 | `setTunEnabled()`（`:476`）走 `updateTunOptions → prepareActivation`，是**又一次完整 activation**，过程中会 `release()` 系统代理再 `resumeDesiredProxy`，造成闪断 |
  | 撤销不可表达 | 撤销已启动的内核只能 `stopCore()`（`:466`），它会写 `desiredProxy = false`，把用户上次的接管意图一并改掉——这不是「回到点击前快照」 |

  因此本期新增**一个**命令 `setProxyEnabled(bool)`，在 Controller 内复用现有 activation 与 `ProxyCoordinator`，失败走既有的 `restorePrevious` 回滚路径；「开启中… / 关闭中…」由该命令的 `begin/finish` 派生，无需新增状态字段。这取代 ADR 0046「命令集合不变」一句，也是 U06「Controller 命令不变」的唯一例外。
- **设置里没有「允许接管」偏好开关，本 ADR 不新增。** 现状只有 `restoreProxy`（启动时是否恢复上次接管）与 `desiredProxy`（上次是否接管的结果）。首页总开关就是接管意图本身；「偏好关、总开关开」这一组合在现有字段下不可达，删除该表述。TUN 的启用仍在「设置 › 网络与内核」的 TUN 管理工具里，它同时是「是否启用 TUN」与「现在是否用 TUN 接管」，本期不拆分。
- 首页不再展示大幅流量曲线、CPU/内存、内核路径；这些在「数据」与「设置」。

## 验证边界

实施后按交互契约的完整任务链复核：开关的**六个**可见状态各自可复现——已接管 / 内核运行中·未接管 / 已关闭 / 开启中… / 关闭中… / 失败：<原因>（与分层设计 P3 表首行一致），其中「已关闭」与「内核运行中·未接管」是两个不同状态，不得合并；手动策略组点击即生效、失败回滚；自动策略组无切换按钮；840×560 下控制区之后仍能看到若干节点行；窄窗长节点名省略而延迟不被挤出。真实 Windows 实机、人工读屏与发行资格不因本 ADR 获得验证。
